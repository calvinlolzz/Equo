01 問題定義 & 設計原則
問題陳述

現有流程要求使用者在建立一個可用的分帳群組之前，依序完成 9 個步驟。其中幣別設定、角色選擇為強制中間步驟，發票辨識為獨立節點，結算依賴手動觸發。這導致：新用戶首次完成設定的轉換率偏低；任何中途放棄的使用者都必須重頭開始；非 Premium 使用者感知到流程因 paywall 而截斷。

設計目標
核心指標
首次設定完成率 +20%（基準待定義）
步驟壓縮
主流程從 9 步壓縮至 5 步，減少 44%
感知負擔
每個步驟只問使用者一件事
零手動計算
結算在每次新增支出後自動更新
設計原則（第一性原理）
合併，不是刪除
幣別選擇是必要資訊，但不需要獨立頁面。合入「建立群組」表單底部。
後置選配
角色權限預設為「成員可記帳」。需要限制時，由管理員進群組設定修改。
狀態，不是動作
結算是一種即時狀態，不是使用者觸發的動作。移除手動更新按鈕。
位置決定感知
發票辨識不是獨立步驟，是「新增支出」的輸入方式之一。非 Premium 看到入口，點擊才顯示 paywall。

情境錯誤碼前端行為

幣別未選擇即送出 CURRENCY_REQUIRED highlight dropdown，toast 提示

支出金額 ≤ 0 AMOUNT_INVALID inline 欄位錯誤
分攤對象全部取消勾選 SPLIT_EMPTY toast「至少選一位分攤對象」，儲存 disabled
付款人不在分攤對象中 — 允許（付款人替他人代墊的場景合法）
結算計算逾時（>5s） SETTLEMENT_TIMEOUT 顯示 loading skeleton，背景 retry × 3，失敗顯示 banner 提示稍後重新整理
邀請連結已過期（24h） INVITE_EXPIRED 獨立錯誤頁，提供「請群組管理員重新產生連結」說明
非 Premium 點擊拍照發票 — Bottom sheet paywall，主流程不中斷，可手填繼續
離線狀態新增支出 NETWORK_ERROR 本機暫存，連線恢復後自動同步（v2 再實作，此版顯示 toast）

v2

OCR 流程、欄位對應、多張發票合併、錯誤辨識人工修正 UI。目前為 placeholder，等 Premium Sprint 補入。

07 為什麼這樣還不夠 — 挑戰清單

「每個需求都應該被質疑。如果你沒辦法刪掉至少 10% 的需求，代表你想得不夠用力。」

— 第一性原理審查框架
⚡
Step 1「登入 / 快速試用」還需要嗎？
為什麼使用者在看到任何價值之前就要登入？競爭對手 Splitwise 讓人先建群組再問帳號。「快速試用」應是預設路徑，登入應在使用者自願儲存資料時才觸發（Progressive Authentication）。目前 SDD 未定義這個分岔。
🔢
「首次設定完成率 +20%」是從哪個基準來的？
基準數字標示「待定義」。沒有基準就沒有成功條件。設計文件必須在 Sprint 開始前確認當前的 conversion funnel 數據：各步驟的 drop-off rate、平均完成時間、最常放棄的頁面。否則這個目標無法驗收。
🧮
最少轉帳演算法（Minimum Cash Flow）的時間複雜度上限是多少？
MCF 是 NP-hard 問題的近似解。群組 100 人、1000 筆支出時的計算時間是否能保持在 SLA 內？文件目前只說「非同步執行 + WebSocket 推送」，但沒有定義最大成員數、最大支出筆數、以及降級策略（超過閾值時切換近似演算法）。
💱
多幣別匯率「來源 TBD」是重大風險。
匯率 API 是金融數據，有法律風險（不同地區的金融資訊揭露規範）、有延遲問題（即時 vs 每日快取影響使用者體驗與帳務準確性）、有費用問題（Open Exchange Rates 商業方案費用不低）。這個 TBD 必須在 v1 發布前解決，不是 v2。
🔒
邀請連結 24 小時過期 — 這個數字從何而來？
旅遊場景中，群組可能在旅行前一週就建立好。24 小時的邀請有效期會逼迫管理員重新產生連結，增加摩擦。建議改為 7 天，或由管理員自設。安全性考量應明確記錄在文件中，而非用隱性假設決定 magic number。
📊
沒有定義任何 Analytics / Telemetry 規格。
如何知道 v1 是否成功？需要定義關鍵事件追蹤：group_created、member_added、expense_added、settlement_viewed、share_tapped、paywall_triggered。每個事件的屬性（group_size、member_count、amount、currency、is_premium）都要在 SDD 中規格化，而非留給 Engineering 自行決定。
08 效能基準 & SLA

所有指標必須在 staging 環境通過壓測後才能進入 production。以下為 v1 的最低可接受標準（MAR）。

09 AI-First 路線圖

分帳是一個資料密集、決策重複性高的問題域，是 AI 介入的理想場景。以下路線圖從最小 AI 足跡（OCR）出發，逐步演進至主動智能代理。

NOW
發票 OCR（Premium v2）
拍照 → 自動辨識金額、日期、商店名稱。技術選型：Google Cloud Vision API 或 AWS Textract（需於 Premium Sprint 前完成 PoC 與費用評估）。準確率目標：金額欄位 >95%，日期欄位 >90%。辨識結果可人工修正，修正資料不回傳訓練（隱私）。
NEXT
智能分類建議
根據支出描述（「炸雞排」→ 餐飲、「計程車」→ 交通）自動標籤分類。模型：本地 on-device 小模型（<5MB）或後端 embedding 查找，不需要 LLM。用途：月報表、支出分析儀表板（v3 功能前置資料基礎）。
NEXT
結算建議訊息自動生成
將結算清單（「A 付 B $350」）轉換成自然語言訊息草稿：「嘿，這次日本行算清楚了！Amos 要付 $350 給 Jill，記得在這週內完成 ✌️」。一鍵複製分享，降低通知摩擦。技術：rule-based template + 可選 LLM 潤稿。
FUTURE
主動異常偵測
偵測異常支出（金額遠超群組歷史均值、同一天重複新增相似金額）並主動提示使用者確認。預防誤操作造成的帳務糾紛。需要足夠的歷史數據才能啟動（新群組不適用）。
FUTURE
自然語言記帳
「我剛付了 1200 塊的火鍋，四個人平分」→ 自動解析金額、付款人（當前使用者）、分攤方式，生成支出草稿供確認。技術：小型指令微調模型或 function calling。隱私模式：全部在本地處理（需評估設備端模型可行性）。
10 基礎設施韌性

系統在失敗時的行為比在成功時的行為更能定義使用者對產品的印象。以下為 v1 必須實作的韌性機制。

資料一致性
冪等 API 設計
所有 POST 端點必須接受 client_request_id（UUID），後端去重複。防止網路重試造成重複支出。前端所有 mutation 必須帶此欄位。
即時通訊
WebSocket 降級策略
WebSocket 不可用時，降級為 30 秒輪詢（polling）。前端顯示「即時更新已暫停」badge。不影響新增支出等核心操作。
結算引擎
計算任務隊列
結算計算透過消息隊列（Redis Queue 或類似）非同步處理。高峰時排隊，不阻塞 expense 寫入。隊列積壓監控告警閾值：>50 任務。
匯率服務
本地快取 + 熔斷
匯率每小時從外部 API 更新，寫入本地快取。外部 API 不可用時，使用最後一次成功的匯率（最多 24 小時），前端顯示匯率取得時間戳。
邀請系統
連結有效期重設計
預設有效期改為 7 天（原 24h 不合旅遊場景）。新增「永久連結」選項（管理員可開啟，風險自負）。過期提示直接在錯誤頁提供重新產生入口。
資料備份
群組資料匯出
使用者有權匯出群組所有支出記錄（CSV / JSON）。這不是 v1 功能，但資料結構必須從 v1 開始設計為可匯出（避免之後重構）。GDPR 合規準備。
災難復原目標（DRO）
指標目標說明
RTO（恢復時間目標） < 1 小時 從服務中斷到完全恢復的最長可接受時間
RPO（恢復點目標） < 5 分鐘 最多可接受遺失的資料量（以時間計）
資料庫備份頻率 每 5 分鐘增量 + 每日全備 符合上述 RPO 要求
11 刪除清單 — 不應該存在的東西

「最好的零件是沒有零件。最好的程式是沒有程式。最好的流程是沒有流程。你能刪掉的每一個步驟，都是一個不會出錯的地方。」

— 第一性原理工程哲學
✕
「手動更新結算」按鈕（已刪）
v1 已正確移除。但需確認後端是否殘留對應 API endpoint — 如果有，也應同步廢棄，防止前端未來不小心重新引用。
✕
強制角色設定步驟（已刪）
已正確後置。需確認預設值（member 可記帳）是否符合 95% 以上的使用場景。若未來數據顯示大多數管理員會立即修改預設值，則需重新評估後置的代價。
✕
Email 驗證信（建議刪除或後置）
SDD 未提及，但典型 App 會有。如果存在，應移至第一次使用後 24 小時才觸發（Jobs-to-be-done 完成後再驗證）。在使用者完成第一筆支出之前發送驗證信是流失使用者的最快方法之一。
✕
Onboarding 教學 Tooltip（建議不做）
如果流程需要 tooltip 才能理解，問題在流程本身，而非使用者不會用。v1 的目標是把流程設計到不需要任何說明文字。所有 tooltip 都是流程設計失敗的補丁。
✕
「分享」和「結算」分成兩個獨立按鈕
目前 Step 5 規格裡，結算狀態、分享方式、標記已付款是三個分開的互動。使用者最常見的動作是「看完結算 → 分享給群組」，這兩個動作應合為一個主要 CTA，次要動作才是「標記已付款」。
✕
Emoji picker 在建立群組時（建議移除）
群組圖示是裝飾性欄位，在首次設定流程中出現會分散注意力。應移至群組建立完成後，在群組設定頁才提供。每個首次流程的頁面只應該有一件事。
