# Equo 算好 Software Design Document

版本：2.0  
狀態：Draft  
主軸來源：`docs/equo_sdd_v2.html`  
產品前提：90% 使用情境發生在手機上，手機版是主產品，網頁版是輔助入口。

## 1. 文件目的

本文件取代原本偏「產品總覽」的 SDD，改以 `equo_sdd_v2.html` 的核心流程改版作為主軸。設計重點不是堆功能，而是降低首次使用摩擦，讓使用者在手機上用最少步驟完成分帳的第一個有效結果。

核心方向：

- 首次主流程從 9 步壓縮為 5 步。
- 每一步只問使用者一件主要事情。
- 登入後置，不在使用者看到價值前阻擋。
- 幣別併入建立群組，不作為獨立頁。
- 角色權限後置，預設成員可記帳。
- 結算是即時狀態，不是手動動作。
- 發票辨識是新增支出的輸入方式，不是獨立流程。
- 手機版優先，網頁版不新增手機沒有的核心能力。

## 2. 平台定位

### 2.1 手機版

手機版是主要產品，占預估使用量 90%。

手機版要求：

- 首頁直接呈現目前應收、應付、群組、待辦與最近支出。
- 常用操作放在底部導覽與底部 sheet。
- 新增群組、新增成員、新增支出、結算分享都要能在小螢幕完成。
- 彈窗採 bottom sheet，不使用桌面式大型 modal。
- sheet 開啟時背景不可捲動。
- 關閉按鈕與主要 CTA 必須在手機上容易點擊。
- 夜間模式、文字對比、觸控範圍必須優先檢查。
- 初期以 PWA 手機網頁為主，後續再評估原生 App。

### 2.2 網頁版

網頁版是輔助入口，占預估使用量 10%。

網頁版用途：

- 產品展示與早期試用。
- 桌面檢視群組、支出與報表。
- 匯出 CSV / JSON / HTML，未來可延伸 PDF。
- 帳號、備份與客服協助入口。
- 不建立與手機版不同的核心流程。

## 3. 問題定義與設計原則

### 3.1 問題陳述

舊流程要求使用者在建立一個可用的分帳群組之前，依序完成過多步驟。其中幣別設定、角色選擇、發票辨識與手動更新結算都被放成獨立節點，造成首次使用負擔過高。

典型問題：

- 新用戶還沒看到分帳價值，就被要求登入或設定太多項目。
- 幣別與角色是必要資訊，但不應打斷主流程。
- 發票辨識若做成獨立節點，非 Premium 使用者會覺得流程被截斷。
- 結算不應要求使用者手動更新，系統應自動產生最新狀態。

### 3.2 設計目標

- 首次設定完成率提升 20%，基準需用實際 funnel 數據補齊。
- 主流程從 9 步壓縮至 5 步，減少約 44%。
- 每個步驟只處理一個主要決策。
- 新增、編輯、刪除支出後自動更新結算。
- 非必要設定後置，不阻擋首次完成。
- 手機版在 375px 寬度可完整操作。

### 3.3 第一性原理

- 合併，不是刪除：幣別是必要資訊，但併入建立群組。
- 後置選配：角色權限預設為成員可記帳，需要限制時再進設定修改。
- 狀態，不是動作：結算是系統狀態，不是手動按鈕。
- 位置決定感知：發票辨識是新增支出的輸入方式之一，不是獨立步驟。
- 先讓使用者得到價值：登入應在備份、跨裝置或分享前才明確要求。
- 能刪掉的流程就刪掉，不能刪的流程要合併或後置。

## 4. 核心流程改版

### 4.1 現況 9 步

1. 登入 / 快速試用。
2. 建立群組。
3. 設定主幣別。
4. 新增成員。
5. 設定角色權限。
6. 新增支出。
7. 發票辨識。
8. 手動更新結算。
9. 一鍵分享。

### 4.2 目標 5 步

1. 快速開始 / 登入後置。
2. 建立群組，包含主幣別。
3. 新增成員，角色預設後置。
4. 新增支出，包含手填與拍照入口。
5. 結算與分享，自動更新。

### 4.3 手機優先流程

手機上應呈現為一條短路徑：

1. 首頁點「建立群組」或第一次使用時直接進入建立群組。
2. 輸入群組名稱，選主幣別。
3. 加入成員或先使用離線成員名稱。
4. 新增第一筆支出。
5. 系統立即顯示「誰付給誰」與分享入口。

登入觸發時機：

- 使用者要備份資料。
- 使用者要跨裝置接續使用。
- 使用者要建立正式邀請連結。
- 使用者要同步多人資料。

## 5. 各步驟 UI 規格

### 5.1 Step 1：快速開始 / 登入後置

路由建議：`/start`

手機 UI：

- 主要 CTA：「開始分帳」。
- 次要 CTA：「登入」。
- 使用者可先建立群組，不必先註冊。
- 當使用者要備份或邀請真實成員時，再提示登入。

欄位：

| 欄位 | 型別 | 規則 | 必填 |
| --- | --- | --- | --- |
| 使用模式 | enum | 快速開始 / 登入 | 是 |
| Email | string | 登入時才顯示 | 條件必填 |
| 密碼 | string | Email 登入時顯示 | 條件必填 |

### 5.2 Step 2：建立群組

路由建議：`/group/new`

欄位：

| 欄位 | 型別 | 規則 | 必填 |
| --- | --- | --- | --- |
| 群組名稱 | string | 1 到 40 字元，不可空白。placeholder：「日本旅遊 2026」 | 是 |
| 主幣別 | enum | 預設 TWD，常用排序：TWD / JPY / USD / EUR / KRW | 是 |
| 群組類型 | enum | 旅遊 / 聚餐 / 室友 / 家庭 / 活動，可選 | 否 |

設計決策：

- 群組圖示不放在首次建立流程，移到群組設定。
- 建立成功後進入新增成員。
- 建立者自動加入群組並成為擁有者。

### 5.3 Step 3：新增成員

路由建議：`/group/:id/members`

欄位：

| 欄位 | 型別 | 規則 | 必填 |
| --- | --- | --- | --- |
| 邀請方式 | enum | 邀請連結 / QR Code / 手動輸入名稱 | 擇一 |
| 顯示名稱 | string | 離線成員使用，1 到 20 字元 | 條件必填 |
| 頭像 | person/avatar | 預設人形頭像，可之後修改 | 否 |
| 角色 | enum | 新增時不強制顯示，預設 member | 後置 |

設計決策：

- 最少 1 位成員即可繼續。
- 角色權限改到群組設定內管理。
- 預設角色為「成員可記帳、可查看」。

### 5.4 Step 4：新增支出

路由建議：`/group/:id/expense/new`

欄位：

| 欄位 | 型別 | 規則 | 必填 |
| --- | --- | --- | --- |
| 輸入方式 | tab | 手填 / 拍照。拍照為 Premium 入口，非 Premium 顯示 paywall sheet | 是 |
| 金額 | decimal | 正數，最多小數 2 位 | 是 |
| 幣別 | enum | 預設群組主幣別，可覆蓋 | 是 |
| 付款人 | member_id | 預設當前使用者 | 是 |
| 分攤對象 | member_id[] | 預設全選，至少 1 人 | 是 |
| 分攤方式 | enum | 平均分攤為預設，自訂金額 / 比例為 v2 | 是 |
| 描述 | string | 0 到 100 字元 | 否 |
| 日期 | date | 預設今日，可往前選 | 否 |

儲存後行為：

- 立即建立支出。
- 前端 optimistic update。
- 後端或資料層觸發結算重算。
- 返回群組支出列表。
- 顯示「已新增支出」提示。

### 5.5 Step 5：結算與分享

路由建議：`/group/:id/settlement`

欄位：

| 欄位 | 型別 | 規則 | 必填 |
| --- | --- | --- | --- |
| 結算狀態 | computed | 每次支出 CRUD 後自動更新 | 自動 |
| 分享方式 | enum | 複製連結 / LINE / 原生分享 | 否 |
| 標記已付款 | boolean | 每筆轉帳可個別標記 | 否 |

設計決策：

- 不提供「手動更新結算」主要按鈕。
- 主要 CTA 應是「分享結算」。
- 次要操作才是「標記已付款」。
- 若結算尚未完成，顯示 skeleton，而不是空白或錯誤。

## 6. 手機版與網頁版差異

### 6.1 手機版實作要求

- Bottom sheet 為主要表單容器。
- 單手可完成新增支出。
- 金額、付款人、分攤對象必須在第一屏附近可操作。
- 成員選擇使用 chip / checkbox，不使用密集表格。
- 刪除確認使用 App 風格 sheet。
- 分享使用原生 share sheet 優先，無法使用時提供複製連結。
- PWA 加入主畫面作為 v2 必做。

### 6.2 網頁版實作要求

- 保留同一組流程與資料模型。
- 可使用較寬的資訊布局顯示報表與群組列表。
- 報表、匯出、帳號管理可比手機版更完整。
- 不應把網頁版做成另一套管理後台，避免產品分裂。

## 7. API 與資料結構

目前產品使用 Supabase。以下 API 可視為服務層契約，不代表一定要建立傳統 REST 後端；可以由 Supabase RPC、Edge Function 或未來 API server 實作。

### 7.1 核心 API 端點

| Method | Path | 說明 |
| --- | --- | --- |
| POST | `/api/v1/groups` | 建立群組，包含主幣別 |
| POST | `/api/v1/groups/:id/members` | 新增成員 |
| PUT | `/api/v1/groups/:id/members/:uid` | 後置更新角色 |
| POST | `/api/v1/groups/:id/expenses` | 新增支出並觸發結算 |
| GET | `/api/v1/groups/:id/settlement` | 取得最新結算 |
| PATCH | `/api/v1/groups/:id/settlement/:sid` | 標記付款狀態 |
| POST | `/api/v1/groups/:id/invites` | 產生邀請連結 |
| POST | `/api/v1/invites/:token/accept` | 接受邀請 |

### 7.2 Group

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| id | uuid | 主鍵 |
| name | string | 群組名稱，1 到 40 字元 |
| base_currency | string | ISO 4217，例如 TWD |
| type | string? | 旅遊 / 聚餐 / 室友 / 家庭 / 活動 |
| created_by | user_id | 建立者 |
| created_at | timestamp | 建立時間 |
| archived_at | timestamp? | 封存時間 |

### 7.3 Group Member

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| id | uuid | 主鍵 |
| group_id | uuid | FK groups |
| user_id | uuid? | 有帳號成員 |
| app_member_id | string | 離線或本機成員識別 |
| display_name | string | 顯示名稱 |
| role | enum | owner / admin / parent / member / child / guest |
| avatar | string | person 或自訂頭像資料 |
| photo_url | string? | 帳號照片 |
| joined_at | timestamp | 加入時間 |

### 7.4 Expense

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| id | uuid | 主鍵 |
| group_id | uuid | FK groups |
| amount | decimal(12,2) | 正數 |
| currency | string | ISO 4217，預設 base_currency |
| paid_by | member_id | FK group_members |
| split_with | member_id[] | 分攤對象，至少 1 人 |
| split_mode | enum | equal / custom_amount / ratio |
| description | string? | 0 到 100 字元 |
| category | string? | 餐飲 / 交通 / 住宿 / 其他 |
| expense_date | date | 預設今日 |
| receipt_url | string? | 收據照片 |
| client_request_id | uuid | 冪等去重 |

### 7.5 Settlement Snapshot

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| id | uuid | 主鍵 |
| group_id | uuid | 群組 |
| version | integer | 結算版本 |
| status | enum | pending / ready / failed |
| transfers | jsonb | A 付給 B 的最少轉帳清單 |
| calculated_at | timestamp | 計算完成時間 |

### 7.6 Settlement 計算邏輯

每次支出新增、編輯、刪除後都應觸發重算。

策略：

- 小群組直接同步或快速非同步計算。
- 結果寫入 `settlement_snapshots`。
- 前端訂閱群組資料更新或輪詢取得最新狀態。
- 多幣別支出以群組主幣別結算。
- 匯率來源與快取策略必須在 v1 前確認，不可長期 TBD。

大群組降級：

- 20 人以下：目標 p99 小於 1 秒。
- 20 人以上：可切換近似演算法或背景隊列。
- 超過限制時前端顯示「結算更新中」，不可阻塞新增支出。

## 8. 邊界條件與錯誤處理

| 情境 | 錯誤碼 | 前端行為 |
| --- | --- | --- |
| 群組名稱空白或超過 40 字元 | GROUP_NAME_INVALID | inline 欄位錯誤，建立按鈕 disabled |
| 幣別未選擇 | CURRENCY_REQUIRED | highlight dropdown，toast 提示 |
| 新增成員 0 人即繼續 | MEMBER_MINIMUM | 繼續按鈕 disabled，提示至少 1 人 |
| 支出金額小於等於 0 | AMOUNT_INVALID | inline 欄位錯誤 |
| 分攤對象全部取消 | SPLIT_EMPTY | toast「至少選一位分攤對象」，儲存 disabled |
| 付款人不在分攤對象 | 無 | 允許，代表代墊 |
| 結算計算超過 5 秒 | SETTLEMENT_TIMEOUT | skeleton，背景 retry 3 次，失敗顯示 banner |
| 邀請連結過期 | INVITE_EXPIRED | 錯誤頁，請管理員重新產生 |
| 非 Premium 點拍照 | 無 | paywall bottom sheet，主流程不中斷 |
| 離線新增支出 | NETWORK_ERROR | v1 顯示 toast，v2 寫入本機暫存並恢復後同步 |
| 重複送出支出 | DUPLICATE_REQUEST | 使用 client_request_id 去重，前端不新增第二筆 |

## 9. 權限模型

角色：

- owner：完整管理權限，可刪除群組與移除成員。
- admin：可新增支出、邀請成員、管理一般帳務。
- parent：家庭模式管理者，可查看與管理子女相關帳務。
- member：可新增支出、查看群組帳務。
- child：只能看與自己相關的支出與結算。
- guest：只能檢視，不能新增、編輯、刪除。

規則：

- 使用者只能讀取自己參與的群組。
- 角色更新只能由 owner/admin/parent 執行。
- guest 不可新增支出。
- child 的查詢結果需在資料層限制，不只靠前端隱藏。
- 邀請預設角色不可高於邀請者可授權範圍。

## 10. 效能基準與 SLA

所有指標需在 staging 通過後才進入 production。

| 操作 | 指標 | 目標 | 降級行為 |
| --- | --- | --- | --- |
| 建立群組 | p95 latency | 小於 300ms | optimistic UI，背景同步 |
| 新增支出 | p95 latency | 小於 500ms | optimistic UI，本機暫存 |
| 結算推送 | 端到端延遲 | 小於 2s | skeleton，5s 後 toast |
| 結算計算 | p99 執行時間 | 小於 1s，20 人以下 | 20 人以上切近似或背景隊列 |
| 首頁載入 | LCP | 小於 1.5s，4G | skeleton，分頁載入 |
| API 可用性 | uptime | 99.9% / 月 | 離線 banner，本機暫存 |
| 即時連線 | reconnect | 指數退避，最大 30s | 顯示「可能不是最新」badge |

壓測情境：

- Baseline：100 concurrent users，每群組 5 人，50 筆支出。
- Peak：1,000 concurrent users，群組 2 到 30 人混合。
- Stress：單一群組 50 人，500 筆支出，同時觸發結算。
- Soak：Baseline 負載 24 小時，檢查記憶體與連線穩定性。

## 11. 基礎設施韌性

v1 必須定義失敗時的行為。

### 11.1 冪等 API

所有新增類操作都應帶 `client_request_id`。後端若收到同一 request id，回傳原結果，不新增第二筆資料。

適用：

- 建立群組。
- 新增成員。
- 新增支出。
- 標記付款。
- 產生邀請。

### 11.2 即時更新降級

優先順序：

1. Realtime / WebSocket。
2. 30 秒輪詢。
3. 使用者手動刷新。

斷線時：

- 顯示「資料可能不是最新」。
- 不阻擋新增支出。
- 重新連線後自動載入最新結算。

### 11.3 結算任務隊列

高峰時結算不可阻塞支出寫入。

設計：

- expense 寫入成功後產生 settlement job。
- job queue 背景計算。
- 隊列積壓超過 50 任務時告警。
- 前端顯示結算更新中。

### 11.4 匯率服務

匯率不能長期留 TBD。

要求：

- v1 前確認資料來源。
- 至少每日快取。
- 外部 API 失敗時使用最後一次成功匯率，最多 24 小時。
- 前端顯示匯率時間戳。

### 11.5 邀請有效期

v2 文件指出 24 小時不符合旅遊場景。建議：

- 預設有效期 7 天。
- 管理員可重產生連結。
- 可評估永久連結，但需明確提示風險。

### 11.6 災難復原

目標：

- RTO：小於 1 小時。
- RPO：小於 5 分鐘。
- 資料庫備份：每 5 分鐘增量，每日全備。

## 12. Analytics 與成功指標

v2 文件指出原 SDD 缺少 telemetry，這是必補項。

需追蹤事件：

| 事件 | 說明 | 重要屬性 |
| --- | --- | --- |
| app_started | 開啟 App | platform, viewport, theme |
| group_created | 建立群組 | group_type, base_currency |
| member_added | 新增成員 | method, member_count |
| expense_added | 新增支出 | amount_bucket, currency, split_mode, group_size |
| settlement_viewed | 查看結算 | group_size, transfer_count |
| settlement_shared | 分享結算 | channel |
| payment_marked | 標記付款 | transfer_amount_bucket |
| paywall_triggered | 看到付費入口 | source |
| backup_enabled | 開啟備份 | auth_provider |
| invite_accepted | 接受邀請 | role, group_size |

成功指標：

- 首次建立群組完成率。
- 建立群組到新增第一筆支出的完成率。
- 新增第一筆支出耗時。
- 結算頁查看率。
- 分享結算點擊率。
- 邀請連結接受率。
- 備份啟用率。

## 13. AI-First 路線圖

AI 功能先不應干擾主流程。所有 AI 功能都應以「先產生草稿，使用者確認」為原則。

### NOW：發票 OCR

定位：Premium v2。

能力：

- 拍照自動辨識金額、日期、店家。
- 自動填入新增支出表單。
- 使用者可人工修正。

目標：

- 金額欄位準確率大於 95%。
- 日期欄位準確率大於 90%。
- 修正資料不回傳訓練，保護隱私。

### NEXT：智能分類建議

能力：

- 根據描述自動建議分類。
- 例如炸雞排歸餐飲，計程車歸交通。
- 優先使用 rule-based 或小模型，不需要一開始使用大型 LLM。

### NEXT：結算訊息草稿

能力：

- 把結算清單轉成容易分享的自然語言。
- 使用者可一鍵複製或分享。
- 初期可用模板，後續再評估 LLM 潤稿。

### FUTURE：異常偵測

能力：

- 偵測同一天重複金額。
- 偵測遠高於群組平均的金額。
- 儲存前提示確認。

### FUTURE：自然語言記帳

能力：

- 「我剛付了 1200 塊火鍋，四個人平分」轉成支出草稿。
- 不直接寫入，必須讓使用者確認。

## 14. Backlog

### v1 必須

- 5 步手機主流程。
- 登入後置。
- 群組建立含幣別。
- 角色權限後置。
- 新增支出後自動更新結算。
- 邀請連結有效期改為 7 天。
- 基礎 analytics 事件。
- 冪等 request id。
- 手機 PWA 基礎。

- 自訂分攤比例 / 金額。
- 離線支援與 IndexedDB 暫存。
- 多幣別匯率正式來源。
- WebSocket / polling 降級。
- 收據照片 Storage 權限。

### v3

- 週期性支出。
- 群組範本。
- 智能分類。
- 結算訊息自動生成。
- 匯出 CSV / JSON / PDF。
- 客服或管理支援工具。

## 15. 刪除清單

以下項目不應存在於主流程，或應後置。

### 15.1 手動更新結算按鈕

結算是狀態，不是動作。新增、編輯、刪除支出後系統自動更新。

### 15.2 強制角色設定步驟

角色權限預設 member，管理者之後再調整。

### 15.3 使用前強制 Email 驗證

若一定需要驗證，應在使用者完成第一筆支出或要備份時再要求。不要在看到價值前要求驗證。

### 15.4 Onboarding tooltip

若流程需要 tooltip 才懂，表示流程本身還太複雜。優先簡化流程。

### 15.5 結算與分享拆成兩個主要按鈕

使用者最常見流程是看完結算後分享。應以「分享結算」作主要 CTA，標記付款是次要操作。

### 15.6 建立群組時選 emoji 圖示

群組圖示是裝飾性欄位，移到群組設定，不阻擋首次建立。

## 16. 對現有產品的改良方向

依 v2 SDD，現有產品下一輪改良應優先做：

1. 重新整理首次使用流程，讓快速試用預設進入建立群組。
2. 建立群組表單只保留群組名稱、主幣別、類型。
3. 新增成員時隱藏角色設定，角色移至群組設定。
4. 新增支出 sheet 重新排序欄位，先金額、付款人、分攤對象。
5. 結算區移除任何「手動同步 / 手動更新」感，改成自動狀態。
6. 邀請連結有效期改為 7 天。
7. 補 analytics 事件設計。
8. 對每個新增操作加入 client_request_id，避免重複資料。
9. PWA 化，讓手機使用者可加入主畫面。
10. 把 AI 助手保持隱藏，未來只以輸入方式回到新增支出內。
